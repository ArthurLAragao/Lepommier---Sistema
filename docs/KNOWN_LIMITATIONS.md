# Known limitations

**Phases 0–6 implement foundation, identity, registry, inventory/production, sales/orders/full payments/refunds and operational cash control. This is not an operational store release. Phases 7–9 remain pending. See PROGRESS.md for the actual current gate result.**

- Business dashboards/reports, promotional sending, backup/restore acceptance and pilot remain unavailable. Operational cash opening/movements/counted closing/review/reconciliation are implemented; this is not full accounting or bank/provider settlement reconciliation. Real customer purchase/payment/refund history is queried separately; no invented metrics or debt panel.
- Schema includes necessary registry, inventory/production and restrictive order/payment/refund/cash-foundation tables. No speculative ingredient tables, public registration, cloud authentication, email dependency, WhatsApp integration or default administrator.
- No real customer/catalog file was supplied or imported. CSV fixtures are synthetic. Actual store columns/data quality and a reviewed real import remain unverified. UTF-8 CSV only, comma/semicolon, 256 KiB/100 rows/20 columns; no Excel/Windows-1252 conversion, updates/merges or fuzzy identity matching. Birthday needs a complete date (1900 onward); Brazilian phone normalization does not guess missing digits.
- Previews are bounded memory-only, five global/two per actor, valid 15 minutes with up to 60 seconds cleanup plus garbage collection. Restart requires new review; closed metadata keeps 30 days. No durable pending-upload queue or closed-job UI. Atomic import uses the local security lock/20-second transaction deadline; larger imports/high-throughput multi-host use are not accepted. Completed retries require the same choices; minimal export is not a roundtrip backup.
- Anonymization removes intended identification from the active DB/evidence references, cancels pending previews and preserves safe history/IDs. It cannot recall delivered browser data/downloads or rewrite backups/DB diagnostic archives. No legal-compliance or forensic-erasure guarantee. See CUSTOMER_PRIVACY.md.
- Product photos/upload are omitted; neutral placeholder only. Whole-unit integer pricing, text shelf-life/storage references and optional restricted estimated cost do not establish automatic shelf lives, weight pricing or full profitability. Historical sales price snapshots are implemented and tested in Phase 5. Receipt cost snapshots are not cash expenses or paid invoices; no discarded-cost estimate is invented.
- Inventory accepts only finished whole units at one location, 1–100,000 per command and 1 trillion per batch. Aggregate API balances are decimal strings. No ingredient use, recipe consumption, multi-location stock, backdating, editable batch identity/expiry, returns, partial reservation fulfilment or physical-count wizard. Wrong metadata uses reviewed compensating entries; no automatic repair. Unknown expiry is explicitly acknowledged and eligible after dated stock under the initial owner-review policy; software does not guarantee food safety.
- Legacy INTERNAL reservations remain valid. New ORDER reservations have restrictive composite OrderItem/product/quantity ownership. Expired allocation blocks handover and stays traceable; explicit cancellation/recreation is required, with owner-approved full refund when paid. No automatic reallocation/partial fulfillment/backorder.
- Stock operations retain actor/key/result for database lifetime. The browser pending key is in component memory only: a page/browser reload loses the local uncertain request, requiring history review before a new operation. No durable offline command queue or request transfer between accounts. Shared security-lock serialization and current per-batch list aggregation are suitable only for the bounded local design; large-volume performance has not been accepted.
- Five active accounts (owners included), one current session per account and a 12-hour absolute lifetime are initial enforced policies to validate against a real shift. No separate inactivity timeout or forced first-login password change is implemented. Owners distribute chosen initial/reset passwords privately.
- Login budgets persist and limit audit/password work but cannot prevent a local malicious process from consuming available attempts. Source budgets reflect a loopback, five-user deployment; LAN/shared-proxy behavior has not been accepted.
- Audit has safe whitelisted metadata and append-only protection, with failed-login rate limits/coalesced denials. Long-term audit retention, archival and disk-capacity policy still need operator decisions. The API exposes the latest 50 events to owners; no browser audit-review page exists yet.
- Local owner recovery is tested through its explicit stdin automation interface on an isolated DB. Its normal interactive password prompt is implemented but has not been validated in a human operator terminal session. Recovery requires an existing active owner and privileged local maintenance; checking one configured port does not discover every possible application process. It does not repair arbitrary direct-SQL corruption or reopen setup.
- Windows filesystem mode flags do not establish an ACL policy. The operator must restrict private key, database, `.env` and backup access. A compromised OS/database administrator is outside the browser security boundary.
- The native Argon2 package was executed on Windows x64/Node 24.19.0 only. Other architectures/OS installations need native dependency verification.
- Local HTTPS cookie attributes were tested through the API; a complete TLS/proxy deployment was not executed. HTTP loopback has an explicit Secure-cookie exception. No public/LAN hosting is authorized. Do not forward setup through a proxy.
- Development PostgreSQL Compose exists, but Docker remains unavailable on this verification path. Docker execution is unverified. Real PostgreSQL 17.10 ran through the existing portable test harness; it is not a production service installation. The existing portable package lacks pg_dump/pg_restore. A private manual pre-migration row snapshot and unchanged table fingerprints do not establish full backup/restore; no additional backup tool was installed.
- Backup/retention tooling, clean restore, full operational restart/disconnected-operation checks, production Compose/image, update lifecycle and store pilot remain later gates. Portuguese guides cover identity, customer/catalog/CSV and stock/production; human operator acceptance remains pending. No real stock counts, supplier receipts or production records were supplied/imported.
- Browser automation used installed Edge in an isolated headless profile at 1366×768 and 390×844, with keyboard, reduced-motion, overflow and automated accessibility checks. Human employee usability and assistive-technology review have not occurred.
- Two existing non-fatal upstream Zod optimization-comment warnings remain in the frontend build. Dependency audit covers known advisories at install time and is not a security guarantee or penetration test.
- Cream/green colors and the text wordmark are provisional. Remote mobile, cloud sync, fiscal/bank integration, store delivery, ingredient costing and messaging are not included.

See PROGRESS.md for executed evidence and TEST_MATRIX.md for remaining release scenarios. Stop at the Phase 6 checkpoint before full Phase 7 business reporting. Do not use this build for daily store operations.

Phase 5 financial confirmation is manual: no payment-provider/bank execution or verification, card data collection, automatic WhatsApp, delivery, partial payments/refunds, split tender, deposits, installments or store credit. A successful DB transaction does not physically charge/refund money; external payment followed by failed/uncertain recording requires review, never automatic recollection. Zero-total completion is rejected; no authorized no-charge path yet. Confirmed order amendments use cancellation/recreation. No fiscal document issuance; detail receipt is non-fiscal. PRODUCTION has no order/payment/customer access. Browser pending command keys are memory-only and do not survive reload.

The persistent Phase 4 manual database and Phase 5 preview are deliberately not migrated to Phase 6 without a verified backup/restore path. Private frozen compatible runtimes preserve both; a separate initially empty Phase 6 preview is for synthetic manual review. See MANUAL_TESTING.pt-BR.md for verified URLs/state and exact restart instructions. Table fingerprints are not a backup; old archives/downloads/browser views may retain earlier PII. Linked collection text is now scrubbed on customer anonymization.

Phase 6 deliberately omits denomination breakdown, arbitrary journal/balance adjustments, reopening/replacement count, partial/chained reversals, cash export and automatic repair. Owner review is separate from financial truth; a genuine count difference does not excuse database drift. Legacy closed Phase 5 sessions retain their original records without an invented counted closing; legacy inconsistent/negative sessions require a separate controlled maintenance decision. Cash history searches exact full session ID and opening-date range; no fuzzy ID/reference search. All source histories are paginated; no high-volume/store-day performance acceptance.

Amounts retain existing per-record caps and a documented 999,999,999,999-cent session aggregate/count cap. A full original-method cash refund is blocked if current expected drawer cash is insufficient; record genuine additional cash first rather than inventing a balance. Reasons/notes must avoid PII; old downloads/backups/log archives still need a retention policy. Browser pending commands remain memory-only and cannot safely reconstruct an unknown physical action after reload.

Current build emits upstream Zod comment optimizer warnings and a bundle-size warning (about 514 kB minified), plus pg client query deprecation and NO_COLOR/FORCE_COLOR test warnings. They did not fail the checks; no dependency upgrade or warning suppression was introduced. Automated Axe/layout/keyboard evidence does not replace a human operator/assistive-technology pilot. Docker, TLS, proxy and LAN were not verified.
