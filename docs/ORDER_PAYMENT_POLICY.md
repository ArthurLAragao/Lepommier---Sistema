# Order state machine, manual payment and refund policy

Delivery and payment are independent. Payment state is derived from immutable records: no Payment = UNPAID; one full Payment without Refund = PAID; one full Refund referencing that Payment = REFUNDED. No mutable paid flag, partial payment, deposit, installments, split tender, customer credit or provider verification.

| Current delivery | Allowed actions                                 | Stock/payment effect                                       |
| ---------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| DRAFT            | Versioned edit; confirm; reasoned cancel        | No reservation/payment until confirmation                  |
| CONFIRMED        | Begin preparation; full payment; cancel         | All items reserved; prices/items frozen                    |
| PREPARING        | Mark ready; full payment; cancel                | Reservation remains; no physical consumption               |
| READY            | Full payment; handover if PAID/eligible; cancel | Entire eligible reservation consumed only at handover      |
| FULFILLED        | Owner full refund                               | Delivery/time preserved; no automatic food return/restock  |
| CANCELLED        | Read history                                    | Terminal; unpaid or fully refunded, no pending allocations |

Immediate COUNTER checkout is a single atomic path through creation/confirmation/payment/fulfillment. It may skip preparation/ready states within that transaction. Manual handover requires READY. Confirmed amendments use cancellation/recreation; never alter a paid order's items/amount silently. Cancellation of a draft has no stock effect. Unpaid confirmed cancellation releases all unconsumed allocations. Paid unfulfilled cancellation commits full refund + cancellation + release together, OWNER only. There is no partial fulfillment or backorder. Expired reservation resolution is cancellation/recreation with current eligible stock; a paid order first requires the corresponding full refund. No arbitrary employee reservation/consumption endpoint is exposed.

Payments require one explicit open CashSession at transaction time and the exact positive order total. CASH requires sufficient tender; change = tender − order total, while the receipt amount is only the order total. PIX/DEBIT_CARD/CREDIT_CARD require explicit employee confirmation and have null physical tender/change. Never collect card numbers/CVV or describe credit-card method as store credit. Zero-total completion is unsupported; zero-price catalog items do not create fake receipts.

Refund requires OWNER, coded reason, original Payment, full original amount, original method, explicit confirmation that the external refund was carried out, and the **current** active CashSession. There is no exception to silently refund a card payment as cash. Concurrent/repeated operations cannot create a second payment/refund. An old payment refunded today links the new refund to today's active session without changing the earlier payment/session. Full cash-management lifecycle and reporting remain Phase 6.

The app records an employee's external receipt/refund assertion. It does not physically charge, verify Pix, contact a card provider or execute a refund. If external money already changed hands and persistence fails, do not charge/refund again blindly. Keep the original operation key, resolve lookup or retry exactly the same request, and inspect order/payment history. A known rejected transaction has no recorded sale/payment/stock effect; the owner must reconcile the external evidence and either record a corrected eligible transaction or handle the external return deliberately. There is no unsupported cash-expense workaround. Browser reload/navigation/session loss loses the pending local key, requiring history review before any new command. No offline durable queue.

All money is integer centavos. Individual order subtotal/total/tender is at most 99,999,999 centavos; intermediate pricing and line discount allocation use BigInt. Persisted financial amounts and cumulative history totals serialize as decimal strings, avoiding unsafe Number conversion. Deferred SQL aggregate checks compare line/order totals, one full payment/refund, genuine allocations and consumption. Financial/events/ledger are append-only; versions reject stale draft/status/payment actions. Methods remain distinguishable for later physical cash queries; Pix/cards have no physical cash contribution. This does not implement a closing report.

Pickup scheduling is entered as a Fortaleza date and minute, strictly future and at most 365 days away at draft create/edit/confirmation. No timezone-less UTC guessing: the server resolves IANA local time and stores the resulting instant. Reservation eligibility must cover that local date and is rechecked against today at handover. Unknown expiry retains the explicit Phase 4 owner-review policy. No shelf-life or food-safety guarantee is inferred.

Customer history definitions: fulfilled total sums snapshots after discounts for FULFILLED orders, including subsequently refunded deliveries, labeled before refunds. Last purchase is max fulfilledAt. Payments received and refunds sum all linked financial rows separately, including paid cancelled orders. These metrics describe only recorded system history, not paper records, profit, order intake or customer debt. Full reporting remains Phase 7.
