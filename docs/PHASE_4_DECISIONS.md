# Phase 4 decisions: finished units only

The inspected baseline was `af7a819` on `main`: Phases 0–3 implemented, three migrations, inventory/production unavailable, 97 unit/API, 63 PostgreSQL and 30 production-browser checks. The existing Fastify/React/Zod/Prisma 7/PostgreSQL architecture, local Node 24 runtime, portable database harness, native dialogs, security lock and privacy projections are reused. No new dependency, global tool, real stock fixture or financial/order table is added. The manual app was paused without stopping or resetting its separate persistent database.

## Schema and accounting

Additive `202610170004_inventory` adds Batch, ProductionRecord, PurchasedProductReceipt, InventoryMovement, InventoryReservation, ReservationAllocation and InventoryOperation. The first three migrations remain byte-equivalent after line-ending normalization. Historical references use Restrict/NoAction. Composite foreign keys enforce matching product/batch and product/reservation identities; deliberate indexes cover product/time/ID history, expiry and operation identities.

The append-only ledger is authoritative. Batch.physical and Batch.reserved are transactionally maintained BIGINT projections. Signed movement totals and outstanding allocations are recomputed before mutation; drift blocks writes. Deferred PostgreSQL constraint triggers compare final transaction projections to cross-table ledger/allocation sums and validate reservation state/quantity. Ordinary CHECK constraints cover row bounds and state shape, not aggregate sums. SQL functions/triggers are maintained in migration SQL because Prisma cannot represent them. Prisma diff checks representable schema; real SQL constraint tests cover the additional safeguards.

Commands accept 1–100,000 whole units. A batch is capped at 1,000,000,000,000 units. Aggregate sums use PostgreSQL numeric and JavaScript BigInt; API balances are decimal **strings**, never JSON numbers. Individual bounded movement/plan quantities remain numbers. Sequence batch numbers (LOT-000001 in the UI) may have gaps. An operator batch reference is normalized with the existing accent/case-insensitive nameKey and unique per product; supplier batch text is separate and nonunique. No mutable product stock field exists.

Ledger entries, purchase receipts and completed operation results cannot be updated/deleted by ordinary SQL operations. A movement must reference its pending operation with matching actor and kind. Batch identity, expiry, source and original notes are immutable. Production's original plan and terminal rows are protected. Corrections append authorized compensating IN/OUT entries, with reason, original movement reference when correcting a record, and before/after context. There is no batch metadata editor, arbitrary stock setter or automatic repair.

## Dates, expiry and quantities

All transaction instants come from the server clock, stored as timestamptz. No opening/receipt backdating input exists. Planned production date and batch expiry are date-only, 2000–2099, evaluated in America/Fortaleza. A dated batch is eligible **through** that local expiry date and blocked afterward. This default requires owner validation; software does not establish food safety. Opening counts can record expired units still present; newly produced/purchased/positive-adjustment batches cannot start already expired.

Unknown expiry is allowed only with an explicit NOT_PROVIDED or LEGACY_COUNT acknowledgement. It is displayed as unknown, remains eligible under this initial policy, and sorts after dated eligible batches. No shelf life is invented from catalog text. FEFO ties use recordedAt then internal ID. Batch metadata cannot be silently changed after receipt. Wrong metadata requires reviewed compensating withdrawal and, where appropriate, a new correctly identified batch; reservations must be resolved first.

Physical includes expired units until explicitly removed. Blocked includes all physical expired units, including any expired reserved units; these columns overlap and must not be added together. Available is the sum of eligible batch physical minus that batch's outstanding reservations. Reserved expired allocations remain traceable, cannot be consumed, and require explicit release before a fresh allocation; no midnight loss, transfer or automatic disposal occurs. See INVENTORY_INVARIANTS.md.

## Production, purchasing, waste and adjustments

Production: PLANNED → IN_PROGRESS → COMPLETED, or cancellation from either open state. Only active PRODUCED/BOTH products can plan/start/complete. Deactivation or origin change blocks start/completion and leaves the record available for cancellation or an explicit catalog correction. Completion atomically receives the positive actual quantity, batch, ledger, audit and result. Zero ready units use cancellation with FAILED_BEFORE_FINISH. Yield shortfall is safe audit context, not a second stock subtraction. Completed quantities remain historical; corrections use adjustments. No ingredients, recipes, supplier accounts, payments or cash expenses are implied.

Purchased receipt accepts active PURCHASED/BOTH products, supplier reference, optional supplier batch and optional bounded integer-centavo cost. Cost is a historical receipt snapshot, visible only to OWNER/MANAGER, never copied over catalog estimated cost. Finished-stock waste is separate from yield shortfall. Waste cannot exceed unreserved physical stock; expired stock may be disposed. EXPIRED requires an expired batch, PRODUCTION_FAILURE requires a produced batch, OTHER requires explanation. PRODUCTION employees may waste only production-source batches.

OWNER/MANAGER adjustments take an explicit positive delta and IN/OUT direction. Existing batch adjustments require a fresh version; a positive adjustment may instead create an explicitly identified batch. Positive entries require eligible batches; negative entries may dispose of expired stock but cannot destroy reservations. Record/production/receipt corrections reference an original movement of the same product and appropriate type. This is a delta review, not a “count found X” wizard. There are no returns until a later explicit business source is implemented.

## Permissions, atomicity and retry

Every protected route reuses named permission checks, exact Host/Origin and non-simple CSRF header. Services reacquire the existing InstallationState security lock and recheck the current active actor/session inside the transaction. Thus a committed revocation wins before the next operation; an already locked transaction finishes before a later account change. There is no frontend-only permission. Explicit selects omit cost for CASHIER/PRODUCTION; CASHIER receives active product identity and sellable availability only, without detailed batches/balances/production. No inventory endpoint selects customer information. Final matrix: PERMISSIONS.md.

Lock order: security singleton → operation identity → sorted product IDs → production/reservation source row → sorted batch IDs → allocations/ledger/projections/audit/result. The singleton deliberately serializes this bounded five-account local app and coordinates catalog/account changes; it is not a high-throughput design. No user interaction or network work occurs under locks. Existing transaction deadline is 20 seconds, acquisition wait 10 seconds. Multi-product internal reservations accept at most 20 distinct products and roll back all lines on failure. Recognized serialization/deadlock codes P2034/40001/40P01 get at most three total attempts (25/50 ms delays). Other errors do not retry. The same command key makes a committed-but-unacknowledged retry safe.

InventoryOperation binds actor + UUID key + kind + SHA-256 of canonical typed payload. Same key/payload returns its pointer-only recorded result; changed payload returns a structured conflict. Mutation, audit and result commit together. Actor-scoped lookup also checks current kind permission. Operations are retained for the database lifetime; there is no expiry cleanup. A future archive must preserve operation identity/result or explicitly change the guarantee. No raw request or supplier notes are stored in the idempotency record.

The browser freezes the payload and key while a result is uncertain and provides lookup/retry of that same request. Confirmed 400/403/404/409 errors allow correction; connection/5xx uncertainty does not silently generate a new key. Dialog Escape/close respects pending resolution. Keys are in component memory only: reloading/closing the browser loses the local pending request, so the operator must inspect history before a new entry. No auth tokens enter browser storage. This limitation is explicit; a durable offline command queue is not implemented.

## Reconciliation, audit and boundaries

Reconciliation returns structured ledger/projection/allocation findings under inventory.reconcile. It changes no stock/history; it appends only a safe access/finding-count audit event. Inconsistent availability is blocked and labeled, not presented as a reliable zero. No diagnostic result claims accurate historical availability for arbitrary dates.

Audit records lifecycle, units, coded reason, non-sensitive IDs, delta/before/after and yield shortfall. It excludes supplier text, operational notes, request bodies, secrets and customer data. Inventory notes/history are operational records with role-restricted access; employees must avoid unnecessary personal information. Append-only history is not backup/restore, and long-term capacity/archival remains an operator decision.

Reservations are internal foundations only: see RESERVATION_CONTRACT.md. No employee reservation/consume endpoint, fake order, stock-linked sale, payment, cash, ingredient or marketing feature exists. Verification uses isolated synthetic records; no actual opening counts or production records were supplied/imported. See PROGRESS.md for executed evidence and the acceptance gate.
