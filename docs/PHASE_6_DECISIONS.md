## Scope and permission decisions

CashSession remains the same identity and opening float/actor/time with restrictive existing payment/refund links. One shared active store drawer remains the policy; Phase 6 does not introduce cashier assignment. OWNER/MANAGER explicitly open, read current/history, post additions/withdrawals/expenses and close. Only OWNER reviews or posts linked reversals. CASHIER uses the active session through existing sales/payment permissions and reads only its ID/opening actor/time; no drawer float/totals/history/movements/close. PRODUCTION has no cash data. This resolves the original future manager-review hint conservatively as owner-only final review, with explicit named permissions rather than convenient UI grants. No financial/customer export endpoint is added.

Cash is operational drawer control, not accounting, bank/card settlement, Pix verification, provider execution, invoice/purchasing/payables, deposits, credit or full business reporting. Payment/refund business rules remain Phase 5. Source rows in cash views expose IDs/order number/method/amount/operator/time, without customer identity/contact/CPF/private notes, product cost, auth data or unnecessary tender details. Authorized order details remain a separate permission-controlled endpoint.

## Additive storage and migration compatibility

006_cash adds CashMovement, CashClosing and append-only CashReview; activity/review versions and a migration-only legacyClosed marker extend the existing CashSession. SQL functions derive all monetary totals; there is no cached mutable balance. Payment/refund/movement triggers increment the activity version, enforce bounds/open session and compare final counters/snapshot. CashClosing stores the exact derived totals, expected/count/difference, explanation, actor/time/version and operation. Restrictive references and custom append-only, lifecycle, direction, unique reversal, source-count and result-target checks complement Prisma's schema.

Existing open sessions keep their identity, float, actor/time, records and links; activity versions initialize from their real source counts. Pre-existing closed rows are marked legacyClosed without inventing a count, closer, explanation or closing snapshot. They remain readable with explicit unavailable historical closing/reconciliation; they cannot be approved as if counted. Column transforms occur atomically inside the migration, without disabling ordinary history/audit triggers. Seven-migration clean and five-migration populated-upgrade checks must pass; no previous migration file is rewritten. The populated Phase 5 upgrade fixture includes an old closed session, a current open session, all four payment methods, an older cash payment refunded in the current session, fulfilled/unfulfilled orders, genuine ORDER allocations/consumption and a legacy INTERNAL reservation. It preserves existing identity and registry markers as well. No database is assumed empty, reset or replaced.

## Money, closing, corrections and reconciliation

See CASH_SESSION_POLICY.md. Single movements/opening/payment/refund remain at most 99,999,999 centavos; movement amounts must be positive. Per-session totals/count and counted cash cap at 999,999,999,999 centavos. Arithmetic is integer/BigInt and SQL numeric; aggregate DTOs are decimal strings, including negative method net receipts and counted differences. Cash tender/change never inflate receipts. Full cash refunds, withdrawals/expenses and negative reversal effects require sufficient expected cash; there is no hidden override. A real authorized cash addition can fund a later cash refund. The system never invents money or executes an external refund.

OPEN/CLOSED derives from closedAt; review status is separate and meaningful after closing. No intermediate counting state or lock while a person counts. Client sends the displayed activity version; server reauthorizes, locks, rejects stale activity and recomputes sources before committing snapshot/closed state/audit/result together. No reopening, overwriting counted cash, auto-midnight closing or automatic transfer of float. Unpaid future orders/reservations do not block closure and can be paid in a later explicit session.

Review is append-only with a separate review version and mandatory note. Owner may approve or mark attention only when the original closed snapshot reconciles. Review never changes original figures and an explanation cannot cure broken source invariants. A narrow financial correction reverses exactly one non-reversal CashMovement, once, with the opposite signed full amount in an explicitly reviewed current open session. It requires owner, reason and confirmation of corresponding physical inverse handling. Original session/entry/snapshot remain unchanged. It cannot target a payment/refund, reverse a reversal, set an arbitrary amount/balance, backdate or silently alter a closing. Annotation-only issues use review; more complex maintenance is a separately controlled procedure.

Reconciliation derives opening + full cash receipts + additions - cash refunds - withdrawals - expenses + signed movement reversals. It checks source counters, payment/order and refund/payment amounts/methods/timing, review counters and immutable closing snapshot equality. Operational count difference is shown separately from integrity findings. No auto-repair exists. Legacy negative expectations or missing legacy closing data are explicitly quarantined for review; they are not fabricated into valid counted closings. Privileged OS/database administrators can bypass protections and remain outside browser authorization boundaries.

## Transactions, response uncertainty and privacy

Retain security singleton -> actor-bound operation -> sorted products -> order -> cash session -> reservations -> batches for sales. Cash-only commands take security/operation then cash row and immutable references, never acquiring product/order locks afterwards. Global transactional rechecks coordinate role/session revocation. Every source insertion locks the active session; closure either follows included activity or wins and later posting fails/rolls back. Stale displayed activity requires explicit review. Existing recognized serialization/deadlock errors have three bounded attempts; other errors do not trigger blind new financial commands. Same actor/key/typed canonical request returns the persisted pointer-only result; changed payload conflicts. Opening/movement/closing/review/reversal effects, audits and results commit together.

Browser pending key/payload stays only in component memory, with lookup/same-request retry and guarded Escape/close. Reload/navigation/session loss still requires history review before issuing a new command; no durable queue is claimed. Financial recording is manual and never implies bank/provider execution. Avoid recipient/customer identity in cash reasons/references/review text. Audit keeps coded context and bounded amount/difference metadata, not full bodies/notes. Cash text has no customer link and is not automatically erased by customer anonymization; it must contain only necessary operational explanations. Retention/backup policy and privileged maintenance remain later acceptance work.
