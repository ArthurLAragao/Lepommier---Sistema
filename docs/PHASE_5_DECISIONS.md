# Phase 5 decisions and boundaries

Starting point: inspected `0b6ce1f` / `0879f7a`, four preserved migrations, verified Phase 4 ledger/reservation and identity/registry protections. The existing strict TypeScript/Fastify/React/Zod/Prisma 7 stack and Node 24.19.0/PostgreSQL 17.10/Edge tooling are reused. No new dependency, global service, cloud API, bank/WhatsApp integration or operational seed is introduced. See PROGRESS.md for actual gate results rather than inferring acceptance from this design.

## Scope adjustments

Payments/refunds require an explicit active CashSession. Phase 5 therefore owns only a minimal additive cash foundation: ID, opening actor/time/float, operation identity, restrictive financial links and a partial unique index allowing one open session. OWNER/MANAGER explicitly open it; it never opens automatically. Authorized OWNER/MANAGER/CASHIER operators share the single active session and each financial record retains its actor. This deliberately resolves the earlier future “assigned cashier session” wording as a shared one-store foundation; individual assignment, complete opening/closing administration and reconciliation belong to Phase 6. closedAt is reserved for that later lifecycle and isolated maintenance tests; there is no employee close endpoint today. The Caixa navigation remains unavailable as a complete module, with limited opening provided inside sales/orders.

Refund approval remains **OWNER only**, preserving the earlier permission matrix. MANAGER may sell, enter/manage orders, record full payments, grant reasoned discounts and open cash, but cannot refund or cancel a paid order. CASHIER may operate sales/orders/full payments and cancel unpaid unfulfilled orders; no discount, refund, cash opening or unrestricted inventory consumption. PRODUCTION has no new order/customer/payment access or queue containing customer data. Permissions are rechecked inside the shared security-lock transaction.

## Schema and money

Additive `202610170005_orders` adds Order, OrderItem, Payment, Refund, OrderEvent and CashSession and extends existing InventoryReservation/InventoryMovement/InventoryOperation. It preserves all four earlier migration files and valid legacy INTERNAL reservations. No second stock subsystem or speculative financial tables. Display order number is a unique immutable sequence, formatted PED-000001, shared by both sources and permitted to have gaps. Restrictive foreign keys retain history through deactivation; financial records/events are append-only.

Order lines snapshot product ID/code/name/version, whole quantity, integer unit selling price and subtotal/discount/line total. Fixed order discounts require OWNER/MANAGER plus a coded reason. Cumulative proportional allocation uses BigInt integer division; deterministic per-line remainder allocation preserves exactly the discount with no negative line or fractional cent. Subtotal and total are capped at 99,999,999 centavos; 1–20 distinct products, 1–100,000 units per line. Intermediate multiplication/discount arithmetic is BigInt and checked before conversion. Order/payment/refund amounts are BIGINT and transported as decimal strings, as are cumulative history sums. Existing product unit price remains a bounded integer number. SQL uses bigint/numeric sums and deferred triggers to compare line snapshots, order totals, full payments, refunds, allocation ownership and consumption at commit.

The server validates both expected product version and price. Any changed version requires explicit cart/draft refresh and review, even if the price itself stayed equal. Confirmation checks again. A confirmed order fixes items, price, customer, source and pickup metadata; amendments require controlled cancellation/recreation. Draft edits replace lines under optimistic versioning, locking up to 40 distinct old/new products while the resulting cart stays limited to 20. No custom product variant or price is invented from notes. Zero catalog prices remain supported, but **zero-total completion/confirmation is rejected** in Phase 5. A zero-total draft may be reviewed/edited; there is no fictitious receipt or implemented no-charge path. A positive-total order may contain an explicitly cataloged zero-price line.

## State, pickup and atomicity

See ORDER_PAYMENT_POLICY.md for transitions and manual payment/refund behavior. COUNTER checkout atomically creates snapshots/order, validates totals/customer/products/cash, reserves all items, records one full payment, consumes all owned allocations, marks fulfilled, appends audit/events and stores the result. Any failure rolls everything back. DRAFT → CONFIRMED → PREPARING → READY → FULFILLED is the manual order flow; the immediate counter transaction may go CONFIRMED → FULFILLED without a fictitious preparation step. Drafts have no reservations/payments. Cancellation is possible before fulfillment; paid cancellation requires an explicit original-method full refund and releases all allocations in the same transaction. Fulfilled refund changes derived payment state, preserving handover/consumption with no automatic food restock.

WHATSAPP means employee-entered source only. It requires a currently active, non-anonymized customer and a future pickup minute within 365 days, interpreted with IANA America/Fortaleza utilities independent of browser timezone. The selected current minute is already past once seconds elapsed; choose a future minute. Confirmation revalidates scheduling. Stored pickup is a UTC instant; allocation requires eligibility through that Fortaleza business date. Earlier collection is permitted after ready/full payment; overdue collection still revalidates current eligibility. Expired/deactivated/inconsistent allocations block handover and remain traceable. The resolution is explicit cancellation/recreation, with owner-recorded full refund if already paid; no silent reallocation or partial fulfillment/backorder. Optional collector/name/note does not create delivery, drivers, fees or tracking.

The existing lock order extends to: security singleton → actor-bound operation → sorted product IDs → order row → active cash session when financial → sorted existing reservation IDs → sorted batches → allocation/ledger/projections/events/audit/result. Internal helper calls reuse already held locks and the same transaction; no nested independent stock transaction, network/provider work or user wait under locks. Existing serialization/deadlock recognition and three-attempt bounded retry remain. The singleton coordinates customer anonymization, catalog/account revocation and these local bounded operations. This is not a throughput/scaling claim.

## Genuine stock ownership and operation reuse

ORDER reservations reference a genuine OrderItem with a restrictive composite foreign key over (orderItemId, productId, quantity); sourceReference equals orderItemId, which in turn references its real Order. Each item owns at most one reservation. Existing INTERNAL rows keep null orderItemId and are not guessed/migrated into orders. Legacy consumption may retain null reservationId; new consumption records its reservation. Composite movement/reservation product references, deferred order/allocation sum/state checks and operation target binding prevent cross-order consumption or partial fulfillment. The ledger/metadata/audit protections remain; only additive trigger/function extensions accept the new authorized order operation kinds.

The reusable InventoryOperation record now also covers draft create/edit, confirmation, progress, checkout, payment, handover, cancellation, refund and cash opening. No unrelated duplicate idempotency store. Same actor/key/kind/canonical typed payload returns the same pointer-only result; changed payload conflicts. Result and financial/stock effects commit together and remain for database lifetime. Sales lookup checks actor ownership and current action permission, without granting cashier arbitrary inventory.reservations. UI pending key/payload is frozen for same-request retry/lookup; closing/Escape is blocked while uncertain. Reload/navigation/session loss discards component memory, so inspect history before a new transaction. No durable browser/offline queue is claimed.

## Customer privacy and history

Orders keep a customer FK, never a customer name/phone/CPF snapshot. Lists select only current customer ID/name/state, order states/amounts/times and creator; detail permits necessary collection text to authorized staff without CPF, customer private notes, contact/address or product costs. PRODUCTION is denied all order/history endpoints. New selections/confirmation reject inactive/anonymized customers. Existing confirmed history can still be reviewed/refunded/fulfilled by order number after anonymization without restoring identity.

Customer anonymization now transactionally clears pickupPerson, collectionNote and operator notes on linked orders, increments affected versions and rejects reintroduction. Monetary/product snapshots and coded reasons/events remain. Audit and operation results contain only IDs/codes, no personal text. Earlier delivered browser screens/downloads/backups cannot be recalled; this is not forensic erasure or legal-compliance certification. Customer profile history now queries real linked rows: fulfilled order totals after discounts **before refunds**, latest fulfillment, all received payments and all recorded refunds separately. Cancelled paid order refunds are not subtracted from fulfilled totals as though a delivery occurred. No debt/credit panel; only this system's recorded history, not imported paper history.

## Manual environment and acceptance limits

The existing persistent manual DB is intentionally **not migrated**: the portable runtime has no pg_dump/pg_restore and a JSON row snapshot is not a verified full backup. Its Phase 4 compiled API/shared/assets and unchanged entrypoint are preserved privately so Phase 5 builds cannot serve incompatible assets to the old schema. The original launcher starts that compatible runtime and its credentials/data remain unchanged. A separate empty Phase 5 preview is prepared only after isolated migration/browser checks; it uses secure first-owner setup and no operational fixtures. It is a disposable review environment, not a real store migration or production installation. Exact URLs/restart instructions and actual readiness belong in MANUAL_TESTING.pt-BR.md and PROGRESS.md.

Full cash closing, counted cash/differences/additions/withdrawals/expenses/review, complete reporting, backups/restores, production installation and human pilot remain Phases 6–9. No operational store-release claim follows from the Phase 5 gate.
